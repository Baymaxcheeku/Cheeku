Authentication

API key issued by LabStack. Pass this in every request header. Your store can hold two active keys at once, so you can move to a new key before the old one is revoked. A key may have an expiry date; a request made with an expired or revoked key is refused as unauthorized. Header: ls-api-key

API for integrating telehealth and in-person provider consultations — speciality discovery, provider search, appointment booking, document management, and video consultations. All requests must include a valid ls-api-key header.

Instant consult webhooks

If you give us a webhook URL and a signing secret, we POST a small JSON notification to it as an instant consult moves on, so you do not have to poll getInstantStatus to the end. Delivery is at least once: the same event may arrive twice, so treat requestId and event together as the key and make handling them repeatable. A delivery that fails is retried for a while and then given up on, so treat the webhook as a prompt to pull rather than as the only way you will hear.

Events

eventMeaning
consult.claimedA doctor accepted the request. Call getInstantStatus for the joining link.
consult.expiredThe request reached its expiresAt with no doctor.
consult.canceledThe request was withdrawn.
consult.doctor_no_showThe doctor who accepted never joined; the request is open again.
meeting.endedThe consultation call finished.
consult.completedThe consultation was completed.
prescription.readyA prescription is available for the consultation.

Body

json
{ "event": "consult.claimed", "requestId": 4821, "appointmentId": 91245, "storeId": 17, "ts": "2026-09-27T10:31:04.000Z" }

It deliberately carries no patient details — it tells you that something changed and which request it was, and you read the rest from the API.

Verifying it came from us

Every delivery carries an x-labstack-signature header: the HMAC-SHA256 of the raw request body, keyed with your signing secret, hex encoded. Compute the same over the body exactly as received, before any parsing or re-serialising, and compare using a constant-time comparison. Reject anything that does not match.

Appointment

Book an appointment

Creates an appointment (ONLINE teleconsult, HOME_VISIT, or CENTER_VISIT) with a provider or provider group for the authenticated store. Provide either lsProviderId or lsGroupId. The patient's gender and dateOfBirth (or age) are optional. For a patient already on record (same uniqueId), a booking only fills in a gender or date of birth not yet recorded and never changes a recorded one; use POST /api/admin/v1.0/user/updateUserDetails to change them. Supports follow-up bookings and an optional pre-appointment payment link, which defaults to the amount payable for the booking unless a lower paymentAmount is supplied. That link is valid for 16 minutes and the appointment is auto-cancelled if payment is not completed in that window. The store's appointment discounts (see GET /api/v1.0/availability/getDiscounts) are applied automatically to a booking with a confirmed provider slot and procedure; pass couponCode to use one that needs a code. At most one discount applies, and the response's discount object says which. Follow-ups and provider-group bookings never take a discount. storeSuggestedTestIds and storeSuggestedPackageIds recommend lab tests and packages to the doctor. They are shown ahead of everything else when the doctor writes the prescription for this appointment, and the doctor decides whether to prescribe them. They can only be set when booking. Some providers need a ten-digit Indian mobile number that is the patient's own, not shared with another patient such as the main user, a valid email address, and the patient's gender and date of birth (sent as gender and dateOfBirth or age, or already on record for the patient), and cannot take isPaymentRequired, paymentAmount, couponCode or isFollowUp. A booking with one of them that cannot meet this fails with 400 saying why, and nothing is booked. Rarely a booking cannot be completed right now: it then fails with 500, nothing stays booked, and trying again is safe. checkInUrl is the patient's clinic check-in link. At the clinic, the patient opens it and checks in by scanning the QR code at the reception, or by typing the code printed under it where there is one. Check-in opens on the day of the appointment. Once the patient checks in, the appointment is CHECKED_IN with customerArrivalTime set, and your appointments webhook is sent. checkInUrl is set for a CENTER_VISIT at a clinic that offers check-in, and is null otherwise. When it is set, send it to the patient before the visit or open it in your app, as they need it at the clinic; getAppointmentDetails returns it too. Ask your account manager about turning on clinic check-in for your providers.

Cancel an appointment

Cancels an appointment for the store. This GET has side effects. An appointment can be cancelled up to a fixed notice period before its scheduled time -- 30 minutes by default. Inside that period, and for an appointment the patient did not attend, cancellation is refused and the caller is directed to support. An on-demand consult can be cancelled at any time, and an appointment whose provider never joined stays cancellable after its scheduled time. An online appointment whose consultation has already taken place cannot be cancelled, even while it awaits the provider's prescription or diet chart. If your account is set up to run its own appointment operations, appointments of the types you manage are not held to the notice period at all and can be cancelled at any time, including after their scheduled time has passed. An appointment that is already cancelled or already completed, or whose online consultation has already taken place, stays closed either way. Ask your account manager to enable this and to choose which appointment types it covers. A cancellation can occasionally fail temporarily. The appointment is then not reported as cancelled, and repeating the call is safe.

Reschedule an appointment

Reschedules an appointment (or updates the requested time of a not-yet-assigned provider-group request) and refreshes the online meeting link. This GET has side effects. An appointment can be rescheduled up to a fixed notice period before its scheduled time -- 30 minutes by default. Inside that period, and for an appointment the patient did not attend, rescheduling is refused and the caller is directed to support. Three cases are not held to the notice period: a completed online appointment, which is how a follow-up is booked; an on-demand consult; and an appointment whose provider never joined. An online appointment whose consultation has already taken place but which is not yet completed - it is awaiting the provider's prescription or diet chart - cannot be rescheduled; once it is completed, rescheduling it books the follow-up. If your account is set up to run its own appointment operations, appointments of the types you manage are not held to the notice period at all. You can move one at any time, to any time -- including a time that has already passed -- and an appointment you cancelled can be moved back into an active slot. A completed appointment remains closed. Ask your account manager to enable this and to choose which appointment types it covers. A reschedule can occasionally fail temporarily. The appointment then keeps its current time, and repeating the call is safe.

Returns the store's appointment discounts that are live now. Each discount is limited by four whitelist/blacklist filters: provider types, specialities, procedures and providers. Discounts are applied by bookAppointment, which reports the discount a booking received; a discount with a COUPON_CODE condition applies only when that couponCode is sent.

Request an instant consult for a patient

Creates an instant consult request and offers it to the doctors available to your account. The response carries the requestId to poll with GET /api/v1.0/consult/getInstantStatus, and expiresAt — the moment the request stops being offered if no doctor has accepted it by then. Treat expiresAt as the deadline rather than assuming a fixed window. If the same patient already has a request still waiting for a doctor, that request is returned unchanged, with its original requestId and expiresAt, instead of a second one being started. The patient is identified by uniqueId; when you omit it, it is derived from the mobile number and name, and calling again with the same uniqueId updates that patient rather than creating another. Instant consult must be enabled for your account, and a call from an account without it is refused with 403; if it is enabled but no doctors are currently set up to take these, the call is refused with 409 rather than creating a request nobody would answer.

Check an instant consult request
