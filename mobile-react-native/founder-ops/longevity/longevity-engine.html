The longevity engine. Every number a family has, turned into the next right habit.

It reads everything a family shares, keeps it on one timeline per person, marks six areas of health, and turns the ones that need attention into a daily plan, a nudge and the next test. The model explains; rules and code decide. This document is how we build it: Suraj owns the AI and retrieval, Archit the app and data layer.

An area takes its worst fresh signal, so one bad sugar report is not averaged away by good step counts. Cut-offs are the common screening lines a doctor would also use, with Indian BMI cut-offs. Adults only for the numbers; a child's areas come from check-ups and the watch. Built in src/lib/longevity/areas.ts and src/modules/wearables/insights.ts. Trust decides which value wins when two disagree: a lab report beats a home reading, a home reading beats a number remembered in chat. The engine never resolves a contradiction silently; it shows both and says which it is using.

The longitudinal memory

Six layers, each built on the one below.

Why it is built this way

  • A clock, not a birthday. The same bilirubin is safe on day 3 and not on day 6. Thresholds are looked up by the person's clock.
  • Trends, not snapshots. Every number carries its previous value, delta and rate, so "99/64" is read as a 33-point drop.
  • Medicines by ingredient. Three products with vitamin D add up; the ledger catches it.
  • Open loops. A bill listing a test with no result means a result is missing.
  • Corrections are visible. A fact that changes supersedes the old one, and the answer says what changed.
  • Area history is new. Snapshots let us say "your sugar moved from act to watch since March", the moment that keeps people.

Layers 1 to 5 exist in the app today (src/lib/memory, migrations 0002, 0030, 0034, 0042, 0044). Full reasoning in docs/health-memory-layer-spec.md.

Retrieval, as Suraj's research set it

  • Switch the embedder to multilingual-e5-small before launch: Hindi and Hinglish, still 384 numbers, so no schema change. Use the query: and passage: prefixes.
  • Chunk on lines and table rows, so "Haemoglobin" and "11.2" stay together. Never cut mid-word.
  • Re-embed everything once; store the model name on every vector and never search across two.
  • Self-hosted, so report text stays on our servers in India.

Why not retrieval for everything

  • The model must never do arithmetic on health numbers. Values, deltas and marks come from code, exactly.
  • The structured context is small and always complete; retrieval can miss a row.
  • Retrieval answers what structure cannot hold: a doctor's note, a scan impression, advice written on a prescription.
  • Every retrieved chunk is cited back to its document in the answer.
How the model reacts

Same engine output, said the way a good doctor would.

The engine saysSugar at act, HbA1c 6.8%
→
The model says"Your HbA1c was 6.8% in October, up from 6.1% in March. That is the range a doctor treats, so it is worth showing Dr Rao. Meanwhile, a 10-minute walk after meals helps most people. Want me to book a doctor or start a sugar plan?"
The engine saysSugar at watch, fasting 103
→
The model says"Fasting sugar 103 is a little high. An HbA1c shows the three-month picture; you are due one in January. One small habit for now: walk after dinner."
The engine saysTwo values disagree
→
The model says"Your report says 78 kg on 2 Nov; you told me 74 kg yesterday. I am using the report until the next weigh-in. Was 74 from a home scale?"
The engine saysSignal older than 18 months
→
The model says"Your last cholesterol test was in 2024. That is too old to go by, so I have not marked your heart area. A lipid test would tell us where you are."
The engine saysOnly the watch says so
→
The model says"Your watch shows about 5.5 hours of sleep this week." Softer words, no medical claim: a watch estimate is not a sleep study.
The engine saysPregnant, or a child
→
The model saysNo weight or sugar goals, no BMI marks. Only gentle habits for children. Pregnancy questions follow the pregnancy clock and its own red flags.
The engine saysA hard stop in the message
→
The model saysThe model is not called. The answer is the hard-stop card: where to go, what to say, one tap to call.

The model writes; it never diagnoses, never names a disease the person does not already have on record, never tells anyone to start or stop a medicine. It can propose actions only from an allowed list: start a goal, book a test, book a doctor, open a screen.

create table longevity_snapshots (          -- one row a day per person, only when a mark changes
  profile_id uuid references profiles not null,
  day date not null,
  areas jsonb not null,                     -- [{key, status, line, signalKeys}]
  inputs_hash text not null,                -- skip the write if nothing changed
  primary key (profile_id, day)
);
create table longevity_targets (            -- the next test, and why
  profile_id uuid references profiles not null,
  test text not null,                       -- hba1c, lipid, tsh…
  cadence_days int not null,
  next_due date not null,
  why text not null,
  rule_version text not null,               -- which signed cadence table set it
  primary key (profile_id, test)
);
create table report_chunks (                -- retrieval, one person at a time
  id uuid primary key default gen_random_uuid(),
  profile_id uuid references profiles not null,
  document_id uuid references documents not null,
  chunk text not null,                      -- a line or table row, never cut mid-word
  embedding vector(384) not null,
  embed_model text not null,                -- never search across two models
  sample_date date
);
-- RLS on all three: the owner's family only, same rules as documents.
Who builds what

Suraj · AI and retrieval

  • Extraction accuracy on Indian lab formats; low-confidence flags
  • Analyte dictionary: every test name to one key and unit
  • Embedder switch to multilingual e5, row chunking, re-embed
  • Prompt: how the model reads LongevityState and cites
  • Model routing and costs: Haiku, Sarvam or GPT-OSS by evals
  • Longevity eval set: 300 questions in English, Hindi and Hinglish

Archit · app and data layer

  • Three new tables with RLS, migrations after 0044
  • Snapshot writer: recompute areas on any new input, write on change
  • Target scheduler: daily job that opens loops when tests fall due
  • Server-side watch sync into wearable_days
  • The model request carries LongevityState; metering as today
  • Under 300 ms to rebuild one person's state

Athar and clinical lead

  • Area cards, change cards and the Sunday review on Home
  • Plan tasks and nudges, written to the content system
  • Family history: two questions at sign-up
  • Clinical lead signs cut-offs, cadences and every red flag
  • Monthly review of 50 real answers with the clinical lead

How we know it works

Correct

  • 99% of extracted values match the report
  • Every eval answer cites the right number and mark
  • Zero answers below the safety floor

Useful

  • 60% of active users with three or more areas known by day 30
  • Half of due retests booked within 7 days
  • Areas moving from act to watch, tracked monthly

Fast and cheap

  • State rebuilt in under 300 ms
  • Answer starts in under 2 seconds
  • About ₹0.07 a chat, about ₹0 per embedding
